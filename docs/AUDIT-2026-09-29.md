# Moddin Desktop — UI/UX, Functionality & Organization Audit

**Date:** 2026-09-29 · **Commit:** `5168ee1` (`main`, in sync with `origin/main`) · **Tree:** clean
**Scope:** whole repo — Vue frontend, Rust backend, catalog, docs, CI/delivery.

This audit exists to correct [ROADMAP.md](../ROADMAP.md). It found that the roadmap currently
disagrees with the code in both directions: several items marked done are not done, several items
marked open are shipped, and a large amount of shipped work (the AI assistant, the MCP agent, the
community catalog) appears nowhere.

## Summary

Three things dominate everything else:

1. **The declarative engine — the product's entire thesis — cannot install anything.**
   5 of 6 registered built-in specs fail at their first install step. The one spec written
   correctly (`bepinex`) is not registered. "Adding a new mod is one YAML file" is currently false.
2. **The transactional-undo promise does not hold on the capability path.** The transaction record
   is created *after* the files are written, so overwritten game files are backed up in their
   already-modified state, and a mid-install failure leaves orphaned writes with no rollback record.
3. **The UI and the docs are considerably healthier than the pipeline.** Locale parity is
   compile-enforced, the architecture guard is real, 208 Rust tests exist, and the design system is
   coherent. The damage is concentrated in the Rust capability runner and in delivery.

### Two things a maintainer has to do by hand

1. **`catalog.json.sig` is now stale.** The community catalogue changed, and
   `regenerate_catalog.py` refuses to sign without `MODDIN_SIGNING_KEY`. Until
   it is re-signed, the desktop app will fail signature verification on the
   community fetch. That is the correct fail-closed behaviour and it is
   *visible* — but it is a release-blocking manual step, not something this
   change can finish.
2. **The community capability is now `status: planned`.** Its install chain is
   structurally correct (download before extract, digest checked before
   anything is written), but the archive layout of an FPS Unlocker build is not
   something this repository can assert — and the previous version of the file
   asserted it and shipped an install that could not run. It stays `planned`
   until someone verifies it against a real game.

### What this block is really about

Blocks 1 and 2 fixed the *runtime*. This block fixed the *authoring side*, and
the pattern is the same both times: a list of valid step or check kinds lives
in four places across three repositories, and nothing kept them in sync. The
drift was found by a human auditing the source, twice. The parity check makes
the third occurrence a red build instead.

### Two decisions worth reviewing

**`ofxr-bridge` and `uevr` are now `status: planned` rather than fixed.** The
audit treated P0-1 as a YAML-only fix, but their install chains need step
kinds the engine does not have: `ofxr-bridge` extracts to a staging directory
and promotes one named file into the OpenXR `ApiLayers` folder (`extract-zip`
has no target-subdirectory option and `move-file` cannot move a directory),
and `uevr` ships as a git tag that has to be built, so no download or extract
step can consume `pinnedTag`. Marking them `planned` stops them advertising an
install that cannot work. It removes nothing the user can do today — the
library grid still installs both through the working `ofxr.rs` / `uevr_module.rs`
modules. Each spec carries a `safetyNotes` entry naming the exact step
capability it needs.

**The `uninstall:` file steps were removed from three specs.** `run_uninstall`
executes them with `ResolvedConfig::default()`, so any step naming a config
field failed with "config field is missing" — `optiscaler`'s uninstall could
never have run. With the transaction now recording every file a step touches,
rollback is both complete and correct, so the partial file-delete steps were
redundant as well as broken.

### Also fixed in passing

- `run_spawn_process` was pushing `pid:NNN` into `affected_paths`, making a PID
  look like a file to anything consuming that list. Removed.
- `run_move_file` silently renamed a path onto itself. Now rejected.
- `test_support::env_lock` used `.expect()`, so one failing env test poisoned
  the mutex and turned into twelve unrelated failures. Now recovers from
  poisoning, so a real failure stays a single failure.
- A YAML scalar containing `": "` silently becomes a mapping. This bit twice
  during this pass, and it is the most likely authoring mistake for anyone
  writing a `safetyNotes` entry. The parse panic now names the offending
  recipe.

# P0 — Release blockers

## P0-1 · The capability install pipeline fails on its first step for 5 of 6 built-in specs

**[verified]** `run_extract_zip` resolves the archive with `resolve_download_path`
(`src-tauri/src/builtin_steps.rs:711`), which only special-cases a **bare filename** and otherwise
falls through to `resolve_path` (`:686`) — that is, `base.join(candidate)`. Five registered specs
point `archivePathField` at a **URL**:

| Spec | Registered | First install step | Result |
| --- | --- | --- | --- |
| `ofxr-bridge.yaml:84-87` | yes | `extract-zip archivePathField: downloadUrl` | fails |
| `optiscaler.yaml:50-54` | yes | `extract-zip archivePathField: downloadUrl` | fails |
| `cheeky-foveated-dlss.yaml:44-48` | yes | `extract-zip archivePathField: downloadUrl` | fails |
| `reshade.yaml:50-54` | yes | `extract-zip archivePathField: downloadUrl` | fails |
| `uevr.yaml:48-51` | yes | `extract-zip archivePathField: pinnedTag` (a git tag) | fails |
| `openxr-helpers.yaml:40-46` | yes | `registry-write` | works |
| `bepinex.yaml:38-48` | **no** | `download-file` + `extract-zip` | correct but unreachable |

The maintainer already knew: the `run_download_file` doc comment in `builtin_steps.rs` says
*"Until this kind existed, `extract-zip` could only read a path from config, so every recipe that
pointed that field at a URL failed with a file-not-found at install time."* The `download-file` step
was then added to exactly one spec — the one that is not registered.

`move-file` is misused the same way in four specs (`optiscaler.yaml:58`, `reshade.yaml:58`,
`uevr.yaml:56`, `ofxr-bridge.yaml:91`), and `ofxr-bridge.yaml:91` moves from `extractedDir`, a
staging directory that is never created.

**Why it matters:** `docs/SCOPE.md:11` and `docs/MODULES.md:16-18` promise that adding a mod is one
YAML file. It is not. This is the single most damaging finding in the audit.

**Fix:** add the `download-file` step to the five specs (copy the shape from `bepinex.yaml:39-44`),
correct the `move-file` fields, and create the `extractedDir` staging directory in `extract-zip`.
Estimate: < 2 h.

## P0-2 · Backup is taken *after* mutation — Undo cannot recover overwritten game files

**[verified]** `src-tauri/src/capability_runner.rs:266-314`:

```rust
for step in &spec.install {
    let result = builtin_steps::execute_step(step, &step_context)?;   // mutates the game folder
    affected.extend(result.affected_paths.clone());
}
let transaction = if !affected.is_empty() {
    let record = transaction::begin_file_set_transaction(...)?;      // snapshot AFTER
```

Consequences:

- Any pre-existing game file the archive overwrote is snapshotted **in its new state**. `restore_record`
  then restores the mod's file — the original is gone permanently.
- If a step fails mid-loop, `?` aborts **before** any transaction is created. Files already written stay
  in the game folder with **zero rollback**.
- The legacy modules get this right: `optiscaler.rs:575` opens the transaction before the apply loop
  at `:587`. The capability path is a regression against the system it was meant to replace.

`docs/SCOPE.md:98` claims "Transactional Undo | Stable" and the app's own store description claims
*"Every change is previewed, backed up, and reversible"*. Both are false on this path.

**Fix:** open the transaction before the step loop, precomputing the target set from the spec rather
than from post-hoc `affected_paths`. Add a test — there is currently **no** test covering the
step→transaction ordering. Estimate: ~2 h incl. test.

## P0-5 · The AI "install recommendation" flow cannot work from the per-game banner

**[verified]** Two different id spaces are both called `gameId`:

- `App.vue:1952` passes `selectedGame.catalog.id` (e.g. `elden-ring`) to `AiGameSuggestions`.
- `App.vue:121` passes the real `selectedAppId` (e.g. `1245620`) to the topbar path.

`AiGameSuggestions.vue:24` forwards it into `useAiAssistant.ts:393` → `:448` calls
`resolveInstallTarget(context.value.gameId)` → `capability-modules/service.ts:47` does

most prominent entry point, with an untranslated message.

**Fix:** one typed id. A branded `StoreAppId` / `CatalogGameId` pair plus a single resolver closes
this and makes the related `acceptUnsigned: true` below structurally impossible to forget. Estimate: ~2 h.

# P1 — UI / UX

Grouped by theme. Full inventory and evidence in the companion notes; these are the ones that change
the roadmap.

## Information architecture

- **UX-01 (P1) — ten entry points into six modals, with no grouping.**
  `GlobalTools.vue:15-19` renders five undifferentiated sidebar rows (AI assistant, VR system,
  Local AI, Community, Activity) plus a topbar split button and a per-game banner. "Assistente de IA"
  and "IA local" share the **same icon** (`AppIcon.vue:10` has one `ai` glyph), so the two most
  similar entries are the hardest to tell apart. *Fix: distinct icon, and group the five under two
  labelled sections (Gerenciar mods / Ajuda e diagnóstico).*

- **UX-02 (P1) — the AI surface has five different verbs for one dialog.**
  `AiAssistantTrigger.vue:7` opens `author`; `AiTopbarMenu.vue:69-94` offers ask/recommend/audit/
  diagnose/contribute; `AiGameSuggestions.vue:22-36` offers recommend/audit; `useAiModuleActions.ts`
  adds improve/diagnose. The sidebar item defaults to the least discoverable mode. *Fix: one verb
  ("Ask the AI") at every entry point; the mode picker inside the dialog is the only place modes are named.*

- **UX-03 (P2) — the per-game AI banner is a nag that reappears on every game.**
  `AiGameSuggestions.vue:17` keeps `dismissed` in component-local state, and `App.vue:1950` remounts
  it per game. *Fix: persist the dismissal through `services/storage`.*

## Consistency

- **UX-04 (P1) — capability cards can only be in 2 of the 6 states the shared card supports.**
  `CapabilityModulesSection.vue:225` passes `isInstalled(...) ? 'active' : 'available'`, while
  `ModuleCard.vue:44-53` also supports `attention`, `checking`, `planned`, `unknown`. A community mod
  whose checks fail looks identical to a healthy one.

- **UX-05 (P1) — the checklist block is implemented twice; the capability copy bypasses the card.**
  `ModuleCard.vue:130-144` renders `verification.checks`, but the capability section never passes
  `verification` and re-implements the list at `:292-313` with a byte-equivalent `.capability-checks`
  block. *Fix: pass the prop, delete the duplicate.*

- **UX-06 (P1) — the same capability has three different install UIs.**

# What is already good — do not regress this

The audit found more strengths than the summary suggests, and several of them are unusual for a
project this size. Any roadmap change should preserve them explicitly.

1. **Locale key parity is compile-enforced.** `defineLocalizedCopy` (`src/i18n/localizedCopy.ts:11-21`)
   makes pt-BR / en / es key drift a *type* error for every `copy.ts`. All three locales carry 385
   keys with zero drift, and every `t()` key used in `src/features`, `src/components` and
   `src/composables` exists. The real i18n problems are runtime strings from Rust, not missing keys.
2. **208 Rust tests** across 37 of 39 backend files, concentrated exactly where bugs corrupt user
   data: the catalog validator, the transaction store, `path_guard` and the step runner.
3. **`scripts/check-frontend-architecture.mjs` is the best artifact in the repo** — 97 lines, zero
   dependencies, real byte budgets, a feature-root rule, a Tauri-import firewall, CRLF normalization
   so budgets mean the same on Windows and CI. Most projects at this stage have none.
4. **Dialog accessibility is real**: focus trap with an outside-focus branch
   (`useDialogLifecycle.ts:62-73`), Escape, focus restore on close, listener cleanup, `aria-modal`
   everywhere, plus a global `:focus-visible` ring and a global `prefers-reduced-motion` kill switch.
5. **Status is never colour-only.** Every badge pairs a tone class with a text label, and module cards
   vary border colour too.
6. **The trust story is visible in the UI**: signature badge + key fingerprint, an explicit unsigned
   consent checkbox, a backup note in every preview, and a change list with check icons. The
   *mechanism* has holes (F-03); the *design instinct* is right and worth keeping.
7. **The friendly-error pattern** (title + "why" + collapsible raw detail) is the right model — it
   just needs applying consistently instead of being copied three times and skipped eight times.
8. **Zero committed secrets and zero real user paths** — verified by grep; the `C:/Users/me/...` hits
   are all test fixtures. For a project whose premise is "we sign things", this is the hygiene you want.
9. **`docs/SCOPE.md` is current and honest**, including a "What Moddin is not" section that is worth
   more than the rest of the docs combined for anyone deciding whether to contribute.
10. **The release notes are excellent** — user-facing voice, per-release SHA-256, a "What to test"
    checklist, and a candid "Known gaps" section that admits in the project's own words that the
    shipped recipes still pass a URL where a local path is expected. That honesty is a real asset.
11. **Community-repo infrastructure is real** — a keyring with rotation history, a security threat
    model, a contribution guide with a "does this belong here" decision table. The problem is drift
    between the two repos, not a missing process.
12. **Constraining to Windows is the right call and is documented honestly** rather than apologised for.
